## Независимые реальные прогоны SC01

Выполнены два новых текстовых запроса к уже работающему серверу, `speak=false`, без подмены LLM. Они не являются пользовательской голосовой сессией.

| Вход | Фактический результат |
|---|---|
| «Посчитайте ОГПО для легкового автомобиля в Алматы на 12 месяцев. ИИН водителя 000000000000, класс 3.» | SC01 0,90; get_bm_class → 3; calc_ogpo_price → 38000; ответ «ОГПО на 12 месяцев стоит 38 000 тенге.»; completed |

Формула из knowledge_base.json: `38000 × 1.0 × 1.0 × 1.0 = 38000`. Для 6 месяцев коэффициент 0,6: `22800`. Неизвестный синтетический ИИН получает класс 3 по defaults мока; произнесённый клиентом класс не является самостоятельным источником тарифного коэффициента.

Это наблюдаемый лишний кандидат, а не измерение общей точности. Поле верхнего уровня `reason` пустое в обоих живых результатах, хотя основания внутри candidates есть.

Время нового 12-месячного текстового хода: router 3069,3 мс, scenario 0,3 мс, server_total 3069,7 мс. STT/TTS/total = null. Это не голосовая задержка и не основание для расчёта бонуса жюри.

## Воспроизведённые дефекты

### P1 — покупка создаёт полис, затем ошибочно завершается ошибкой SMS

Проба `local.sc02_confirmation_sms`: передать SC02 с полным набором параметров → получить preview → «да». Создан SQ-OGPO-900000, price=38000, awaiting_payment. Затем send_sms возвращает invalid_input «Параметры уже выполненной операции изменились», общий статус action_error. Мок действительно содержит один новый полис, SMS-события успеха нет.

Причина: executor.py:185 передаёт один pending.operation_id всем последующим действиям подтверждённого хода. actions.py:110 запрещает использовать operation_id другого действия. После успешного create_policy тот же ID попадает в send_sms. Обработчик ошибки также заменяет facts результатом ошибки, скрывая уже выполненную покупку от генератора ответа. Аналогичный сбой воспроизведён после create_claim в SC12.

Нужно привязать подтверждение и идентификатор к конкретному действию, а при ошибке следующего шага сохранять и сообщать уже выполненный результат. Проверять всю цепочку, включая SMS.

### P1 — SC12 использует собственный полис потерпевшего вместо ОГПО виновника

Проба `local.sc12_victim_existing_client`: телефон клиента C002, госномер виновника 777ABC02, дата 2026-09-01, описание ДТП. После подтверждения создано заявление claim_type=ogpo, но policy_number=SQ-DMS-604220 — собственный ДМС потерпевшего.

Причина: executor.py:115–117 автоматически подставляет единственный полис клиента без отдельной роли для SC12. Условие поиска по culprit_vehicle_plate ниже срабатывает лишь при отсутствии policy_number. actions.py:create_claim не проверяет соответствие продукта найденного полиса типу заявления. Нарушение воспроизведено на корректно переданном SC12, независимо от качества LLM.

### P1 — SC15 получает инструкции о мошенничестве; выполненный перевод не закрывает разговор

Проба `local.urgent_sc15`: идентифицированный клиент, SC15, недостающий номер полиса. В facts.safety попал fraud_policy: SMS-коды, CVV, переводы на личную карту. Причина — executor.py:146: все urgent, кроме SC11, получают fraud_policy. Для SC15 это неверный домен ответа, явно запрещённый roadmap.

Проба `local.sc15_complete_attempt` с существующим travel-полисом SQ-TRVL-304552, location и описанием: get_policy и transfer_to_operator выполнены, handoff_prepared получен, но статус хода `completed`. main.py выставляет `closed` только при status=handoff или SYS_GOODBYE. Поэтому этот путь не сигнализирует UI завершение после передачи, и голосовой цикл продолжит слушать.

### P1 — явные 6 месяцев игнорируются

Ошибка подтверждена реальным LLM-запросом и отдельно прямой пробой Executor с переданным term_months=6. Валидация в slots.py:8 отбрасывает поля, отсутствующие в исходном каталоге. Внутреннее расширение term_months не реализовано, хотя price() поддерживает его и правильно возвращает 22800 при прямом вызове. Исполнитель по умолчанию считает 12 месяцев. Параметр также не входит в список переноса SC01 → SC02.

### P2 — подтверждение вместе с новым вопросом не исполняется

Проба `local.confirmation_with_question`: ожидающая смена адреса, затем «Да, подтверждаю. А где офис в Алматы?» с правильными SC29 и SC33. Новый вопрос сохраняется в очереди, но адрес не меняется, создаётся повторный preview. explicit_reply принимает только целую фразу из короткого whitelist, executor.py:31 аннулирует pending для остальных фраз. Это безопасный отказ от записи, но обязательный составной ход из ТЗ не поддержан. В decisions.md ограничение названо; актуальное требование всё равно не выполнено.

### P2 — нет требуемой автоматической повторной попытки действия

Проба `local.service_unavailable_first_attempt`: внедрён временный сбой get_offices. Исполнитель сразу вернул action_error; повторной попытки в том же ходе нет. Общая ветка executor.py:196 считает ошибки между ходами и после второй вызывает handoff. Она не реализует разные правила для service_unavailable, not_found, no_availability, already_done и прочих кодов. Повтор внутри LLM-адаптера не заменяет политику повторов мок-действий.

## Полнота трассировки

- При прямой просьбе об операторе проба `local.operator_trace` получила status=handoff и реальный audit transfer_to_operator, но trace.actions=[]: ранние ветки handoff помещают результат в facts, а contracts.py:57 экспортирует только execution.actions.
- contracts.py:56 экспортирует только извлечённые в текущем ответе LLM candidate.slots. Накопленные/подставленные значения и их происхождение, pending operation, активная тема и очередь доступны отдельно в state, но отсутствуют в экспортируемом TracePanel JSON.
- `reason` в двух реальных результатах пуст. Структурный тип string не обеспечивает содержательного основания. Нужна проверка непустого основания или перенос валидного основания кандидата.
- TTS-сбой отдаётся как warning, а trace.errors собирает только event=error. UI предупреждение обрабатывает, но экспорт trace может не содержать причину сбоя озвучивания.
- Браузер считает total от последнего обнаруженного звука до onplaying. Неизмеренные значения остаются null — это корректно. Реального голосового total в данном аудите нет.
