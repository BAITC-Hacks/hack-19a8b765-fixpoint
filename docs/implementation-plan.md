# План реализации MVP: backend и frontend

Статус: проектирование, не описание уже работающего приложения. Требования и ограничения — в `../AGENTS.md`. Этот документ определяет минимальный состав реализации. Провайдеры LLM/STT/TTS и конкретные версии зависимостей выбираются при подключении интеграций.

## 1. Что пользователь получит

Одна страница в браузере. Пользователь нажимает «Начать разговор», разрешает микрофон, говорит и слышит ответ оператора на русском или казахском. На экране остаётся история разговора. Агент консультирует и выполняет предусмотренные кейсом операции в мок-бэкенде. Подтверждение действий происходит в разговоре.

Обязателен полный каталог из 40 сценариев и трёх системных намерений. Минимальность относится к интерфейсу и инфраструктуре, а не к сокращению требований кейса.

Не делаем регистрацию, личный кабинет, меню разделов, административную панель, редактор сценариев, аналитику звонков, аватары, сложные анимации и отдельное мобильное приложение. Реальные SMS, платежи и телефонию имитируем. LLM и голосовые интеграции должны быть реальными.

## 2. Техническая схема

```text
React + TypeScript + Vite
  ├─ HTTP: создать/получить/закрыть сессию, экспортировать трассировку
  └─ WebSocket: текст, поток аудио, события обработки и ответы
         ↓
FastAPI — один процесс / один worker для MVP с состоянием в памяти
  STT → нормализация → понимание LLM → политика диалога
       → исполнитель → KB / мок-бэкенд
       → текст ответа → TTS → браузер
```

Backend — монолит с небольшими модулями. Frontend — один экран и локальное состояние React. Без Redis, очереди задач, векторной БД, Kubernetes, Redux и системы плагинов. JSON датасета загружаются при старте, данные для записи копируются в каждую сессию. Перезапуск сервера сбрасывает разговоры и изменения моков.

В разработке Vite проксирует запросы на сервер. Для демонстрации предпочтителен один origin: backend раздаёт собранный frontend. Локальный запуск — localhost; удалённый доступ к микрофону — через HTTPS/WSS. Инструкцию запуска и ограничения целевого браузера зафиксировать после реальной проверки.

## 3. Backend: элементы реализации

### B01. Запуск и конфигурация

Файлы: `backend/app/main.py`, `config.py`, `backend/pyproject.toml`, `.env.example`.

- Создать приложение FastAPI, загрузить настройки и датасет один раз при старте.
- Настройки: путь к данным, фиксированная бизнес-дата `2026-10-01`, провайдеры и модели, ключи API, таймауты, пределы аудио, время жизни сессии.
- Использовать типизированные схемы Pydantic. Секреты читаются только сервером, не попадают в API и логи.
- Health сообщает доступность приложения и настроенность интеграций без раскрытия ключей. Отсутствие ключа не мешает локальным тестам, но реальный запрос к этой интеграции возвращает понятную ошибку.
- Ограничить входной текст, длительность записи, размер сообщения и число активных сессий. Начальные инженерные пределы: текст 4 000 символов, запись 60 секунд, неактивная сессия 30 минут; вынести в настройки.

Готово: сервер запускается воспроизводимо; ошибки конфигурации понятны; секретов в ответах нет.

### B02. Загрузка и проверка датасета

Файлы: `data/catalog.py`, `domain/catalog_models.py`.

- Загрузить сценарии, слоты, действия, KB и исходные записи бэкенда.
- Проверить уникальность ID, ссылки сценариев на слоты/действия/очереди/альтернативы, обязательность подтверждений для необратимых действий.
- Разделить ошибки структуры, при которых запуск невозможен, и известные смысловые пробелы, отражаемые в документации.
- Не импортировать dev-разметку и ожидаемые ответы в рабочий маршрутизатор. Они доступны только оценочным скриптам.

Готово: весь каталог доступен; неправильная ссылка обнаруживается с именем файла и поля; исходные JSON не изменяются.

### B03. Модели и состояние сессии

Файлы: `domain/models.py`, `dialogue/state.py`, `data/session_store.py`.

Минимальные модели:

| Модель | Основные поля |
|---|---|
| `Session` | ID, язык ответа, клиент, active_frame, pending_intents, suspended_frames, pending_operation, история, счётчики ошибок |
| `ScenarioFrame` | scenario_id, этап, слоты, происхождение слотов, ожидаемый вопрос, результаты действий |
| `Understanding` | язык входа, предпочтение языка, сценарии/confidence, альтернативы, слоты, continuation, confirmation, новый запрос |
| `PreparedOperation` | operation_id, action, аргументы, версия параметров, preview, статус подтверждения |
| `ActionResult` | успех/data либо error.code/error.message, признак изменения, operation_id |
| `TurnTrace` | поля трассировки из ТЗ, результаты этапов и измерения |

Слоты содержат значение, роль и источник: текущая реплика, профиль или предыдущее действие. Нельзя смешивать телефон для идентификации и новый телефон, собственный полис и полис виновника.

Хранилище в памяти: случайный идентификатор сессии, отдельная копия мок-данных, блокировка обработки хода, журнал выполненных операций и последних событий. Ограничить историю и удалять неактивные сессии. Для локального демо идентификатор сессии служит непредсказуемым токеном доступа; не выдавать это за промышленную авторизацию.

Готово: две сессии не влияют друг на друга; параллельные сообщения одной сессии не выполняют конфликтующие действия.

### B04. Нормализация и валидация

Файлы: `domain/normalization.py`, `domain/validation.py`.

- Нормализовать телефоны, ИИН, госномера, названия городов/стран, даты и числа RU/KK.
- LLM может извлечь значение из свободной речи; детерминированный код проверяет формат и допустимость. Не исправлять неоднозначные цифры догадкой.
- Относительные даты рассчитывать от даты кейса. Срок поездки включает обе границы.
- Проверять ограничения продукта поверх общих enum: например, суммы страхования имущества и несчастного случая различаются.
- Не превращать отрицание «пострадавших нет» в положительный сигнал срочности только из-за ключевого слова.

Готово: проверки покрывают примеры RU/KK, неверные форматы, относительные даты и противоречивые значения.

### B05. Адаптеры внешних API

Файлы: `providers/base.py`, отдельные файлы выбранных провайдеров.

Интерфейсы:

```text
LLM.understand(text, context, catalog) → Understanding
LLM.render_reply(reply_plan, language) → текст
STT.transcribe(audio_stream, audio_format) → partial/final transcript
TTS.synthesize(text, language) → аудиофрагменты + формат
```

Подключить по одному реальному провайдеру на роль; универсальную платформу выбора не строить. Вызовы асинхронные, с ограниченным таймаутом, отменой и максимум одним повтором при временной ошибке. Невалидный ответ LLM не передаётся исполнителю. Заглушки используются только в тестах и явно обозначаются.

До выбора проверить на реальном аудио: казахские буквы, смешанную речь, телефон по цифрам и группам, задержку, формат потока и качество TTS. Наличие заявленного языка у провайдера не заменяет такую проверку.

Готово: адаптеры можно заменить без изменения сценариев; реальная поддержка обоих языков подтверждена отдельно.

### B06. Понимание и маршрутизация

Файлы: `dialogue/router.py`, `dialogue/prompts/`.

- Передать LLM описания всех сценариев, `not_this_if`, компактные примеры, состояние и пользовательскую реплику.
- Получить структурированное понимание, проверить ID и диапазоны confidence, удалить дубликаты сценариев.
- Распознавать подтверждение и новый запрос одновременно, например «Да, записывайте. А анализы покрываются?».
- При ожидаемом ответе на слот использовать компактный анализ продолжения. Он всё равно должен обнаруживать новую тему и срочность; при их наличии запускать полный выбор сценариев.
- Не запускать полный каталог заново для уже установленного продолжения. Не создавать отдельную обученную модель классификации намерений.
- Неверный JSON: одна попытка исправления схемы, затем понятный отказ обработки без действий.

Готово: получены predictions на 104 репликах, метрики и список ошибок; отдельно проверены контекстные реплики «да», «завтра» и номера телефонов.

### B07. Политика и контроллер диалога

Файлы: `dialogue/policy.py`, `dialogue/controller.py`.

Контроллер — единственная точка, решающая следующий шаг. Он применяет пороги уверенности из AGENTS.md, приоритет urgent, правила языка, очередь тем и возврат к прерванному сценарию.

Каждый ход возвращает `ReplyPlan`: тип ответа, разрешённые факты, один следующий вопрос, результат действия, необходимость подтверждения или передачи оператору. Этот объект отделяет бизнес-решение от формулировки ответа.

Порядок работы: проверить новую срочность и просьбу оператора → обработать контекст и извлечённые данные → актуализировать активный сценарий → проверить подтверждение → определить следующий допустимый шаг. Срочное прерывание приостанавливает старую операцию; не исполнять её по неоднозначному согласию.

Системные намерения обрабатывать явно. Прощание закрывает разговор, но не отменяет ранее выполненные действия. Короткая благодарность при незавершённом вопросе не всегда означает прощание.

Готово: детерминированные тесты переходов, multi-intent, смены темы, низкой уверенности и выбора очереди оператора.

### B08. Исполнитель сценариев

Файлы: `dialogue/executor.py`, `dialogue/scenario_plans.py`.

Один общий исполнитель и декларативные планы для 40 сценариев. План указывает идентификацию, источники слотов, чтения, условия записи и handoff. Отдельные обработчики нужны только там, где различается бизнес-логика; не создавать 40 копий одного автомата.

Этапы: identify → collect → prepare → await_confirmation → execute → complete. Справочные запросы пропускают лишние этапы. Список `actions` в датасете не означает выполнение всех действий подряд.

Сначала читать профиль и доступные полисы, потом спрашивать недостающее. Если несколько подходящих записей — задать вопрос выбора. Для SC12 разрешён потерпевший вне клиентской базы. Для справочного вопроса не собирать персональные данные без необходимости.

Готово: каждый сценарий имеет исполняемый план и путь до результата либо предусмотренного handoff; заглушка «соединяю с оператором» не заменяет реализуемый сценарий.

### B09. Реестр действий и мок-бэкенд

Файлы: `actions/registry.py`, `actions/clients.py`, `policies.py`, `pricing.py`, `claims.py`, `medical.py`, `communications.py`.

Все 31 действие реализовать с типизированными входами/выходами:

| Группа | Действия | Минимальная реализация |
|---|---|---|
| Чтение | find_client, get_policies, get_policy, get_bm_class, get_claim, check_payment | Поиск в сессионных данных; фильтр по продукту и владельцу/роли; однозначность; ошибки not_found/invalid_input |
| Расчёты | calc_ogpo_price, calc_casco_price, calc_travel_price, calc_property_price, calc_accident_price | Формулы KB обычным кодом, проверки ограничений, деньги без накопления ошибок float |
| Полисы | create_policy, renew_policy, update_policy, cancel_policy | Подготовка, согласие, запись, уникальные номера, новое состояние доступно последующему чтению |
| Заявления | create_claim, create_dispute | Привязка к полису и заявителю; запись заявления/спора; новый номер |
| Запись | book_inspection, book_appointment | Синтетическое расписание, проверка продукта/покрытия, preview без брони, повторная проверка и бронь при execute |
| Справочные | check_coverage, list_clinics, get_offices, kb_lookup | Конкретная выборка KB; условное покрытие сохраняет ограничения и необходимость направления |
| Контакты | update_contact | Проверка нового значения по выбранному полю, подтверждение, обновление профиля |
| Сообщения/обращения | resend_documents, request_document, send_sms, create_callback, create_complaint, report_fraud, transfer_to_operator | Запись события в журнал мока с адресатом/содержанием/очередью; отсутствие внешней отправки |

Для `get_policy` возвращать необходимые полные данные, статус вычислять по датам и изменениям. Для исторического события проверять покрытие на дату события. `check_coverage` не упрощает условие «по направлению, до двух раз» до безусловного обещания оплаты.

У создания полиса различать выдачу номера и активацию после оплаты: не объявлять новый полис оплаченным без события оплаты. Точные правила мок-оплаты, продления, изменения премии, округления и возврата зафиксировать в decisions до реализации этих операций. Для неподдержанного тарифа возвращать явное ограничение, а не нулевую стоимость.

Готово: все действия зарегистрированы, существенные результаты проверены; журнал и изменённые записи подтверждают исполнение.

### B10. Подтверждения и защита от повторов

Файл: `actions/operations.py`.

`prepare` сохраняет снимок аргументов, рассчитанные условия, operation_id и версию. Ответ пользователю называет существенные условия. `execute` допускается только для актуальной операции после явного согласия в нужном контексте.

Изменение аргументов сбрасывает согласие. Подтверждение одной записи не подтверждает все операции в очереди. Для каждой выполненной операции хранить результат; повтор возвращает его без повторной записи. Мутация и регистрация результата выполняются под одной сессионной блокировкой без внешнего await между ними.

Готово: тесты запрета execute без согласия, исправления параметров, отрицания, повторного запроса, прерывания и одновременной отправки.

### B11. База знаний и генерация ответа

Файлы: `data/knowledge.py`, `dialogue/replies.py`, `domain/speech_text.py`.

Для маленькой статической KB достаточно адресуемых разделов JSON, без RAG-инфраструктуры. Контроллер выбирает нужные разделы; генератор получает ReplyPlan, факты, результаты действий и язык. Пользовательские строки передаются как данные, не как инструкции.

Стандартные вопросы, ошибки и подтверждения формировать шаблонами RU/KK. LLM использовать для естественного объяснения фактов и сложных ответов. Так меньше вызовов и ниже риск искажения суммы или результата. Для неподдержанного определения — честный ответ и оператор, не справка из памяти модели.

Хранить `display_text` и `speech_text`: смысл одинаковый, в речи числа естественно произносятся, персональные данные маскируются. Не озвучивать техническую трассировку.

Готово: ответы краткие, подтверждения точные, неизвестный факт не выдумывается; действие с ошибкой не описывается как успешное.

### B12. Голосовой конвейер

Файлы: `api/voice.py`, `providers/stt_*.py`, `providers/tts_*.py`.

Использовать потоковую передачу аудио и partial STT для отображения. Бизнес-обработку начинать только по завершённой реплике, не по промежуточному тексту. В MVP ходовой разговор: во время ответа микрофон не отправляет запись; кнопка остановки звука позволяет начать новую реплику. Автоматическое перебивание голосом не входит в первый минимум.

Начало/конец реплики определять детектором речи с ручной кнопкой завершения как запасным способом. Пауза внутри номера не должна преждевременно завершать ход: порог тишины подобрать на тестах RU/KK. Длительная тишина не вызывает LLM.

Формат входа согласовать один раз при открытии потока: предпочтительно моно PCM16 через AudioWorklet; адаптер приводит частоту к требованию STT, не просто меняет число в заголовке. Для выхода выбрать один потоковый формат, который надёжно воспроизводится в целевом браузере, и явно передавать codec/sample_rate. Контейнерные фрагменты нельзя считать независимыми файлами без проверки формата.

Сбой TTS не отменяет выполненную операцию: показать текст, разрешить повторить только озвучивание. Сбой STT не создаёт пользовательский ход из пустого текста.

Готово: реальный звук проходит в обе стороны, тишина и паузы корректны, собственный ответ не записывается как речь клиента.

### B13. Трассировка и оценка

Файлы: `tracing/events.py`, `tracing/metrics.py`, `scripts/evaluate_router.py`, `tests/`.

После каждого хода сохранять поля из README, outcome действий и состояние сценария. Каждый этап имеет turn_id и измерение монотонными часами. Отсутствующее измерение — null, не ноль.

Общую голосовую задержку измеряет браузер: от конца речи до фактического начала первого звука на одной шкале `performance.now()`. Если конец речи уточняет серверный VAD, передавать смещение конца речи в аудиопотоке и сопоставлять с временной шкалой записи. Backend получает вычисленную длительность; не вычитает серверное время из браузерного. В трассировке указывать способ измерения. Текстовые ходы и неозвученные ответы исключать из медианы, число исключений показывать.

Оценка маршрутизатора сохраняет predictions в формате эталонного evaluate.py. Отдельно проверять порядок намерений, контекст, действия и голос; эталонный скрипт не покрывает эти свойства.

Готово: экспорт позволяет воспроизвести ошибку, измерения честные, в логах нет ключей API.

## 4. Контракт браузера и сервера

Это внутренний протокол MVP; точные схемы фиксируются перед кодом и разделяются с TypeScript.

| HTTP | Назначение |
|---|---|
| GET /api/health | Состояние приложения и интеграций |
| POST /api/sessions | Новая сессия, session_id, возможности голоса |
| GET /api/sessions/{id} | Снимок истории и текущего статуса после переподключения |
| DELETE /api/sessions/{id} | Закрыть сессию, освободить ресурсы |
| GET /api/sessions/{id}/trace | Скачать JSON трассировки |
| WS /api/sessions/{id}/stream | Двусторонний разговор |

Сообщения управления — JSON: `type`, `request_id`, `turn_id` при наличии, `payload`. Серверные события дополнительно имеют последовательный `event_id`. Аудио идёт бинарными фреймами; принадлежность и формат задаёт audio.start, завершение — audio.end. На соединении одновременно один входной и один выходной аудиопоток, каждый привязан к turn_id.

| Направление | События |
|---|---|
| Клиент → сервер | text.submit, audio.start, бинарные аудиоданные, audio.end, playback.stop, playback.started, playback.failed |
| Сервер → клиент | session.ready, turn.accepted, transcript.partial, transcript.final, turn.status, assistant.text, audio.start, аудиоданные, audio.end, trace.updated, turn.completed, error |

`playback.started` содержит turn_id и измеренную задержку. Повторные подтверждения воспроизведения не создают новую запись метрики. `request_id` защищает от повторной обработки текстового запроса после сетевого сбоя.

При разрыве соединения клиент не отправляет последнюю команду вслепую. Сначала получает snapshot и результат request_id. Если потеряно аудио ответа, можно повторить озвучивание сохранённого текста без повторного исполнения действий. Незавершённый входной аудиопоток отбрасывается с просьбой повторить. Новую сессию не создавать автоматически при каждом reconnect.

## 5. Frontend: один экран

```text
Saqta · Голосовой помощник                 Новый разговор
Демонстрация · операции выполняются в тестовых данных

                 История диалога
          Клиент: ...
          Помощник: ...

         Слушаю / Обрабатываю / Отвечаю
       [Начать разговор / Завершить реплику]
                 [Остановить звук]

       Введите сообщение…              [Отправить]

       ▸ Диагностика последней реплики
```

На широком экране диагностику можно открыть справа; на узком — под диалогом. Она обновляется после каждого хода и доступна для демонстрации, но не занимает основной экран по умолчанию. Достаточно простой типографики, одного акцентного цвета и понятных состояний кнопок.

### F01. Каркас приложения

Файлы: `frontend/src/App.tsx`, `styles.css`.

Одна страница без роутера. Header, Conversation, VoiceControls, TextComposer, ErrorNotice, TracePanel. Обычный CSS, без тяжёлой UI-библиотеки. Адаптивная ширина, читаемые сообщения, видимый focus, подписи кнопок, работа с клавиатуры. При запуске нет запроса микрофона до действия пользователя.

Готово: страница работает на ноутбуке и узком экране, основные действия доступны без диагностики.

### F02. Состояние приложения

Файлы: `hooks/useSession.ts`, `state/sessionReducer.ts`, `types.ts`.

Использовать useReducer для серверных событий, обычные hooks для устройств. Хранить session_id, сообщения, текущий partial transcript, статус хода, состояние соединения, ошибку и trace. Не копировать бизнес-логику сервера на клиент.

Основные состояния: idle, connecting, listening, processing, speaking, disconnected, error, closed. Таблица переходов запрещает отправку нового обычного хода во время незавершённой обработки. Двойной клик не создаёт две сессии или два хода.

Готово: UI согласован с сервером, сброс очищает историю и медиа, устаревшие события старой сессии игнорируются.

### F03. HTTP и WebSocket

Файлы: `lib/api.ts`, `hooks/useConversationSocket.ts`.

Обёртка над fetch и одним WebSocket. Типизированные сообщения, request_id, обработка sequence/event_id, ограниченное переподключение. Не показывать пользователю сырой stack trace. Повторное соединение восстанавливает snapshot, не повторяет действия.

Готово: закрытие вкладки освобождает ресурсы; временное отключение не дублирует сообщения или операции.

### F04. Запись микрофона

Файлы: `hooks/useMicrophone.ts`, `audio/capture-worklet.ts`.

Получить getUserMedia после нажатия, показать статус записи, передавать поддержанный аудиоформат. Обработать отказ доступа, отсутствие микрофона, занятое устройство и неподдержанный формат. Запись ограничена по длительности; пользователь может закончить реплику вручную.

При speaking отключать отправку входного аудио. После окончания ответа возвращаться к прослушиванию только если разговор остаётся активным. При выходе/сбросе остановить tracks, worklet и AudioContext.

Готово: реальное устройство проверено; индикатор записи правдив; микрофон не остаётся активным после завершения разговора.

### F05. Воспроизведение голоса

Файлы: `hooks/useAudioPlayback.ts`, `audio/player.ts`.

Очередь фрагментов одного ответа, декодирование согласованного формата, воспроизведение без смены порядка. AudioContext активировать пользовательским действием. Зафиксировать момент фактического старта, а не получения первого сетевого пакета.

Кнопка «Остановить звук» очищает очередь и текущий звук, но не отменяет бизнес-операции. При ошибке воспроизведения текст остаётся, показывается предложение повторить звук. Просроченные фрагменты предыдущего ответа не воспроизводить.

Готово: ответы не накладываются, остановка работает, метрика первого звука отправляется один раз.

### F06. История разговора

Файлы: `components/Conversation.tsx`, `Message.tsx`.

Две роли, обычный текст, переносы строк, компактный статус обработки. Partial transcript отображается как черновик и заменяется final, не создаёт множество сообщений. Автопрокрутка только когда пользователь находится внизу истории.

Не требуются markdown-редактор, реакции, вложения, карточки продуктов или интерактивные формы каждого сценария. Подтверждение остаётся голосовой или текстовой репликой.

Готово: текст и озвученный ответ совпадают по смыслу; повтор события не дублирует сообщение.

### F07. Текстовый ввод и ошибки

Файлы: `components/TextComposer.tsx`, `ErrorNotice.tsx`.

Одна строка/компактное поле, Enter для отправки, Shift+Enter для переноса, пустые сообщения не отправляются. Текст идёт в тот же контроллер; это полноценный способ диагностики при отсутствии микрофона.

Ошибки показывать рядом с разговором: понятная причина и одно действие — повторить, разрешить микрофон или продолжить текстом. Не скрывать отказ голоса за успешным текстовым ответом.

Готово: можно пройти сценарий текстом, не обойдя подтверждения и проверки сервера.

### F08. Диагностика

Файл: `components/TracePanel.tsx`.

Сворачиваемая панель: ID/название сценария, confidence, язык, альтернативы, краткая причина, слоты, действия, статус подтверждения и задержки. Можно выбрать предыдущую реплику и скачать JSON. Технические имена видны только здесь.

Отличать preview от execute, успешное действие от ошибки и мок-перевод от реального звонка. Не создавать графики и отдельный dashboard.

Готово: жюри может проверить решение после каждого хода без открытия терминала.

### F09. Новый и завершённый разговор

Кнопка «Новый разговор» закрывает текущую сессию и создаёт чистую: останавливает микрофон/звук, очищает историю и сбрасывает моки. Пока идёт операция, не запускать конкурирующий сброс; дождаться результата либо явно показать незавершённое состояние.

После SYS_GOODBYE или мок-передачи оператору показать итоговый статус. Передача оператору не должна выглядеть как бесконечное ожидание реального человека. Для нового диалога остаётся одна понятная кнопка.

## 7. Минимальная проверка качества

Backend: pytest для формул, нормализации, переходов, подтверждений и ошибок; интеграционные тесты API с подменой только внешних провайдеров. Проверить весь реестр действий и 10 диалогов по поведению. Критичные суммы: 38 000 за пример ОГПО, 15 400 за поездку и 163 800 возврата D07 при заданных условиях.

Frontend: проверка типов и production build; несколько проверок поведения для дублей событий, восстановления соединения и сброса. Сквозной браузерный тест текстового сценария подтверждает результат в моках. Реальное аудио проверяется отдельно вручную на обоих языках: виртуальный микрофон не доказывает качество живой речи.

Приёмка: независимые перефразировки, multi-intent, срочный запрос посреди сбора слотов, смена языка, отказ от операции, смена параметров после preview, неизвестный телефон, несколько полисов, повтор execute, недоступность провайдера и отключение сети после записи.

Внутренний ориентир маршрутизации — ≥95% primary accuracy и full match на dev с разбором всех ошибок, не официальный проходной балл. Задержку оптимизировать после корректности. Отчёт различает локальные тесты, реальные API и реальные голосовые прогоны.

## 8. Что должно лежать в готовом репозитории

- Backend и frontend, файлы зависимостей и lock-файлы соответствующих инструментов.
- `.env.example` без секретов и `.gitignore` для ключей, временного аудио и результатов локального запуска.
- Исходный датасет без изменений, отдельные расширения моков.
- README с точными командами установки/запуска/сборки/проверки и перечнем переменных окружения.
- `docs/decisions.md` с принятыми допущениями, `docs/progress.md` с фактическим состоянием.
- Тесты и скрипт генерации predictions, отчёт об оценке и известных ограничениях.

Не создавать пустые модули только ради совпадения с планом. Объединять небольшие части допустимо, если их ответственность и проверки сохраняются. Каждый этап должен добавлять работающий путь пользователя.
