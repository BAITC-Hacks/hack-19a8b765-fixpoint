# Соответствие FixPoint / Saqta Voice Agent требованиям — 23 сентября 2026

**Оценка: около 70% соответствия требованиям проекта. MVP ещё не прошёл полную приёмку.**

Это экспертная взвешенная оценка реализованных и проверенных возможностей, а не официальная метрика ТЗ, процент пройденных тестов или вероятность успеха у жюри. Разумный диапазон оценки — 65–75%; он отражает неполную проверку реальных диалогов и голоса, а не статистический доверительный интервал.

## Основания и границы аудита

Проверены требования `AGENTS.md`, README датасета, JSON-каталоги и примеры, roadmap, актуальные исходники backend/frontend, настройки и запуск, тесты, отчёты маршрутизации и архив разговоров. Выполнены локальные тесты, production build, валидация датасета, повторный подсчёт сохранённых predictions официальным оценщиком и 11 диагностических проб с изолированным мок-бэкендом. В браузере проверено открытие режима `?jury=1` и возвращение к основному экрану.

База: commit `a0c6520f58ddf4a137c33e391a22fb19a8444af3` и рабочее дерево. Во время аудита другие процессы меняли frontend, capture-диагностику, архивные тесты и файлы развёртывания; новые разговоры продолжали поступать в архив. Поэтому числовые результаты относятся к зафиксированным срезам, а не ко всем последующим изменениям. SHA-256 ключевых файлов и отчётов сохранены в `reports/compliance-audit-2026-09-23.json`.

Новый полный платный прогон 104 запросов не запускался. Сохранённый прогон повторно оценён без API; после него маршрутизатор менялся, поэтому эти метрики не выдаются за измерение последней версии. Физический микрофон, качество звучания казахского TTS, чистая установка на другом компьютере и VPS этим аудитом не проверены. Нет оснований объявлять их ни полностью работающими, ни полностью неработающими.

Исходники бизнес-логики и датасета в рамках аудита не исправлялись. Добавлены этот отчёт и `scripts/audit_compliance.py`; диагностические результаты записаны в `reports/`.

## Маршрутизация: фактически измеренные результаты

Источник: `reports/predictions.json`, `reports/routing_trace.json`, модель в сохранённом отчёте — OpenAI `gpt-4o-mini`. Повторный запуск оригинального `evaluate.py` подтвердил:

|---|---:|
| Верный первый сценарий | **91/104 = 87,5%** |
| Полное совпадение набора намерений | **76/104 = 73,1%** |
| Multi-intent recall | **18/26 = 69,2%** |
| Полное совпадение многоцелевых запросов | **5/13 = 38,5%** |
| Полное совпадение неясных запросов | **0/3** |
| Полное совпадение out-of-scope | **1/4**; основной сценарий правильный у 4/4 |

| KK: primary / full match | **88,9% / 73,3%**, 45 реплик |

Всего 28 неполных совпадений; в трёх записях — ошибки разбора слотов. Медиана сохранённого времени маршрутизации среди 101 записи с измерением — **2489,5 мс**. Это не голосовой total.

Повторяющиеся проблемы: потеря второго намерения в 8 из 13 многоцелевых запросов; лишние сценарии в одиночных и out-of-scope запросах; конкретный сценарий вместо уточнения во всех трёх unclear; путаница SC13/03, SC16/11, SC18/14, SC22/системные намерения. Внутренний ориентир 95% не достигнут, но он не является официальным проходным порогом ТЗ.

Последующие изменения parser и защиты идентификаторов могли исправить часть ошибок. Без нового прогона нельзя численно ни засчитать улучшение, ни утверждать, что все старые ошибки сохранились.

## Воспроизведённые дефекты

Результаты ниже записаны в `reports/compliance-audit-2026-09-23.json`; повторяются командой `scripts/audit_compliance.py` без внешней LLM. Благодаря готовым правильным routing decisions эти пробы отделяют ошибки исполнителя от ошибок распознавания намерений.

1. **P1 — SC12: неверная роль полиса.** Потерпевший C008, госномер виновника `777ABC02`. Ожидается полис виновника `SQ-OGPO-104501`, preview заявления использует собственный `SQ-OGPO-103990`. Причина: автоподстановка единственного полиса профиля (`executor.py:154–164`) предшествует специальной логике SC12, которая срабатывает только при отсутствии `policy_number` (`:216`). Текущий тест использует другого заявителя и не выявляет этот случай.

2. **P1 — SC15: неправильный домен срочных фактов.** При известном travel-полисе и недостающей location результат содержит `safety == fraud_policy` (`executor.py:193`). Без идентификации просто запрашивается телефон, facts пусты. Проверен результат исполнителя, а не конкретная фраза внешней LLM: утверждать, что LLM обязательно произнесёт совет про мошенничество, нельзя. Но единственный переданный срочный источник неверен.

3. **P1 — теряются явно выбранные параметры страхования.** `validate_slots` молча удаляет отсутствующие в исходном каталоге внутренние `term_months` и `package` (`slots.py:8`). ОГПО на 6 месяцев: прямой расчёт **22 800**, через диалог **38 000**. КАСКО Lite для машины 2022 года стоимостью 10 млн: прямой расчёт **200 000**, через диалог **500 000**. Пробелы записаны в decisions.md, но это не делает проигнорированный выбор клиента соответствующим требованию.

4. **P1 — время записи может измениться после согласия.** Preview SC21 показывает **10:00**; если это время стало занято, execute с теми же пользовательскими слотами успешно бронирует **14:00**. Контроллер сравнивает исходные слоты, а не существенный результат preview; backend заново берёт первое свободное время (`actions.py:248`). Это инъекция изменения доступности в изолированном моке, не заявление о наблюдённой гонке в браузере. По требованию следовало предложить альтернативу и запросить согласие.

5. **P2 — составное подтверждение не исполняется.** После preview адреса фраза «Да, подтверждаю. А где офис в Алматы?» с правильными SC29+SC33 оставляет адрес прежним, офис в очереди, статус снова confirmation. `explicit_reply` принимает только целую фразу из whitelist (`executor.py:17`), остальные реплики снимают pending (`:73`). Это безопасно относительно записи, но обязательный составной ход не поддержан.

6. **P2 — отсутствует retry временного сбоя действия.** Внедрён однократный `service_unavailable` в get_offices; вызов сделан один раз, сразу action_error. Общая ветка ошибок считает неудачи между ходами, вместо требуемой одной автоматической повторной попытки и затем handoff. Правила разных кодов ошибки сведены к общей инструкции.

7. **P2 — SC18 не получает документы конкретного заявления.** При переданном `CL-500330` и типе КАСКО выполняются kb_lookup и SMS, get_claim не вызывается. Ответить о недостающих документах конкретного заявления из таких результатов нельзя. Заранее допустимое расширение SC18 из AGENTS/decisions не проведено через исполнитель.

8. **P2 — список действий выполняется слишком широко.** После идентификации через SC25 вопрос «Где офис в Алматы?» вызывает get_offices и send_sms, хотя SMS не просили. Аналогичный риск есть у других справочных сценариев. Это проверяемая демонстрационная SMS, не реальное сообщение, но условность действий по ТЗ нарушается.

9. **P2 — неполная трассировка передачи.** В SC37 audit содержит `transfer_to_operator`, статус handoff, но `trace.actions=[]`: ранние ветки кладут результат в facts, экспорт читает только execution.actions (`contracts.py`, `executor.py:64`). Аналогично устроены некоторые error/payment handoff. Слоты trace — извлечённые значения текущей маршрутизации; накопленные значения и происхождение доступны в state/полном архиве, но не в кратком JSON TracePanel. TTS warning сохраняется в events, но не попадает в trace.errors, собирающий только event=error.

10. **P2 — соединение не восстанавливается из snapshot.** `useSession.ts` при обрыве предлагает новый разговор; повторный connect закрывает предыдущий и делает POST новой сессии. Серверное чтение snapshot есть, но frontend им не восстанавливает текущий разговор. Это анализ кода, отдельный сетевой сбой в браузере не вводился.

11. **P2 — режим жюри не является постоянной боковой трассировкой.** `?jury=1` открывает тот же `dialog.showModal()`, что dev. В браузере в AX-дереве доступны только dev-инструменты; после закрытия модального окна появляется основная кнопка, но трассировки уже не видно. Запустить разговор и одновременно держать такую панель открытой штатным образом неудобно. Параметры dev и jury не разделяют диагностические действия.

Старые дефекты, которые повторно не нужно считать открытыми: использование operation_id предыдущего действия для send_sms исправлено; create_claim проверяет соответствие продукта; SC10/SC15 с полными данными возвращают handoff; архив разговоров реализован; reason имеет fallback из первого кандидата. Старый `docs/project-audit-2026-09-23.md` поэтому не описывает текущее состояние целиком.

## Голос и задержка

Реализованы MediaRecorder, детектор активности, автоматическая отправка после паузы, серверный STT, общий диалоговый конвейер, TTS MP3, автоматическое воспроизведение и повторное включение записи. Во время TTS запись остановлена. Обработаны основные ошибки микрофона и провайдеров. Энергетический детектор отдельно проверяется на синтетических сигналах, паузах внутри номеров и шуме.

В зафиксированном срезе аудита: **25 архивов, 36 ходов, из них 33 аудио**; язык маршрутизации у 31 — ru, у 2 неизвестен. Из 19 аудиоходов с браузерным total: **медиана 6170 мс**, минимум 4522, максимум 14083. Срез сохранён в JSON; поступившие позже разговоры в эту цифру не включены. Ранее в этой же проверке на меньшем наборе было 12 измерений и 6324,5 мс — отличие объясняется поступлением новых сессий.

Эти значения подтверждают наличие измерения от браузера, но не являются контролируемым финальным бенчмарком: состав запросов разный, успешные и ошибочные диалоги смешаны, происхождение аудио отдельно не аттестовано. Аудиоданные не сохраняются, поэтому качество произношения по одному архиву не проверить. Текстовые ходы в голосовую медиану не включались, отсутствующие значения не заменялись нулями. По этому срезу бонус за ≤3 секунды не подтверждается; официальное измерение делает жюри по своему набору.

Не закрыто:

- STT получает законченный файл; передачи частичных гипотез нет. Наличие событий audio.chunk не делает транскрипцию потоковой.
- LLM/STT/TTS имеют разные настройки моделей, но STT/TTS используют `llm.client` и общий ключ OpenAI. Требование независимых провайдеров/ключей выполнено частично.
- Нет штатного отдельного повтора озвучивания сохранённого ответа без нового диалогового хода.
- Натуральное произнесение чисел и маскирование в основном поручены prompt/TTS. Быстрый ответ ОГПО формируется цифрами; отдельного слоя вербализации и систематической проверки произношения нет.
- Нет контролируемого сквозного комплекта RU/KK/mixed с датами, суммами, ИИН, телефоном, сменой языка и результатом действия. Синтетические TTS→STT-пробы из progress.md полезны, но не заменяют живой микрофон.

## Документация, интерфейс и запуск

В переданном пользователем AGENTS.md основной экран требует скрыть текстовый ввод и историю в dev. Первый абзац локального roadmap описывает более поздний интерфейс с видимым полем и историей. Текущий App соответствует этому абзацу roadmap, но расходится с переданным AGENTS. Это явный конфликт требований; его нельзя молча превратить в однозначный UI-баг или объявить полностью согласованным. Он не влияет на найденные бизнес-дефекты и основной вывод.

README также устарел в деталях: обещает отдельный jury-режим без текстового ввода, постоянную трассировку и confidence на главном экране. В проверенном App confidence находится в модальной dev-панели, текстовое поле — на главном экране. Документы progress содержат исторические записи, включая прежний Groq и отсутствие ключа; их нельзя читать как актуальные блокеры.

Локальный React build и FastAPI-контракты проверяются. `start.ps1`/`run.py` и основной docker-compose по-прежнему запускают API+Streamlit, а не главное React-демо; README отдельно даёт корректные команды для React. Появившиеся параллельно VPS/deploy-файлы не считаются проверенным развёртыванием. Новая чистая установка, HTTPS/WSS на целевой машине и доступность выбранных API с неё требуют отдельного запуска.

## Что необходимо до приёмки

1. Исправить SC12, срочные факты SC15, перенос внутренних term_months/package и фиксацию времени брони в подготовленной операции. Это ошибки результата, а не оформления.
2. Поддержать составное подтверждение; разделить обработку кодов ошибок; добавить SC18 get_claim по контексту; ограничить SMS и другие действия условиями сценария.
3. Исправить trace.actions ранних передач, snapshot после обрыва и постоянный jury-режим. Согласовать документы интерфейса.
4. Повторить 104 реальных запроса текущей версией, разобрать все ошибки и добавить независимые RU/KK/mixed-перефразировки, не включая dev-ответы в prompt.
5. Пройти все 10 диалогов с реальной LLM с проверкой итоговых моков; отдельно проверить отказ, составной ход, срочное прерывание, возврат к теме, неизвестные идентификаторы, несколько полисов, исторический случай и повтор события.

`audit_compliance.py` не обращается к API и не меняет существующие сессии. Каждая бизнес-проба создаёт собственный MockBackend в памяти. Он обновляет только файл результатов аудита; агрегаты архива могут измениться при новых разговорах. Predictions и routing_trace являются локальными артефактами `reports/`; для воспроизведения старых чисел их нужно сохранить вместе с отчётом.
